# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # Start dev server
npm run build    # Production build
npm run lint     # ESLint
```

There are no tests. Deploy via `git push origin main` — Vercel auto-deploys from GitHub. Do NOT also run `npx vercel --prod`; that creates duplicate deployments and the CLI deploy frequently hangs.

**Every package a page imports should be in `package.json`, even if it already resolves locally.** npm hoists transitive dependencies to the top of `node_modules`, so a bare `import` of something you never declared works on a dev machine and in `npm run build`, while depending on another package's dependency tree to keep providing it. The guide detail page imported `unified`, `remark-parse`, and `remark-rehype` this way (hoisted out of `next-mdx-remote` → `@mdx-js/mdx`); they are declared explicitly as of 2026-08-23. This was hygiene, **not** the cause of the guides-500 below — don't let it be mistaken for the fix.

**Diagnosing a route that 500s where it should 404:** the failure is happening at *module load*, before any page code runs, so `notFound()` never gets a chance to fire. The tell is that **prerendered pages keep working while on-demand ones 500** — prerendered HTML was generated at build time, so only the runtime path exercises the broken import. Get the real stack with the Vercel MCP `get_runtime_errors` (project/team ids are in `.vercel/project.json`) rather than guessing; a local `npm run build && npx next start` will *not* reproduce it, because `next start` has the whole `node_modules` on disk while Vercel externalizes packages into the function bundle.

**Commit hook:** `.claude/settings.json` registers a `PreToolUse`/`Bash` hook running `scripts/hooks/pre-commit-pull-tiers.mjs`. Before any `git commit` it does two things: (1) pulls live official tier rankings out of Supabase into `heros.json`/`legacy.json` (see the Creator Program section), and (2) stamps today's date into `src/dcdl/data/data-updated.json` for every data file the commit touches. Both are staged into the same commit. It is silent when there's nothing to do and never blocks a commit — don't work around it, and if tier JSON or the stamp file shows up unexpectedly in a commit, that's the hook doing its job.

**Hook gotcha — `git add` must be its own tool call.** The hook is `PreToolUse`, so it runs *before* the Bash command it intercepts, and its date-stamping step reads the **already-staged** file list. Running `git add X && git commit -m ...` as one command means nothing is staged when the hook looks, so it silently stamps nothing and the page keeps its old "Updated:" date. Stage in one call, commit in the next. If it's already been missed, `node scripts/stamp-data-dates.mjs <filename>` stamps it by hand.

**"Updated:" dates** (tier list, best teams, combat cycle, supreme commander) come from `getDataLastUpdated()` in `src/dcdl/lib/data.ts`, which reads the committed `src/dcdl/data/data-updated.json` (filename → ISO date, max across the files a page names). It must NOT go back to `fs.statSync().mtimeMs` — build systems normalise mtimes, so that reported **October 20, 2018** on every deployed page. `scripts/stamp-data-dates.mjs` maintains the file: `--seed` backfills missing entries from git history, and passing filenames stamps them with today (what the commit hook does).

**Fact-check release status against the official posts before writing it.** When a guide draft, page or answer depends on whether something is out yet (a champion, skin, legacy piece, event, mode — the creator-program NDA limits the site to released content), query Supabase: `patch_notes` (per `game`) for what shipped, and the `game_posts` archive (every official Discord announcement since 2024-06, filter by `game` / `kind` / `posted_at`, search `body` with `ilike`) for reveals, events and codes. Run `node scripts/sync-discord-patch-notes.mjs --write` first if the latest post looks stale. A teaser or "coming soon" post is not a release.

## What this is

Quantum Game Guides — a community hub for DC: Dark Legion (primary) plus Godforge, Invokers: Titan Legacy and Void Hunters. Features a champion/legacy database, community tier voting, MDX guides, and an admin panel for managing game data.

**Gotham map** (`app/games/dc-dark-legion/ship-combat-guides/page.tsx` + `ship-combat.css`) — SVG-based interactive deployment planner for Battle For Gotham and Ultimate Battle For Gotham. A **mode switcher** (segmented `.sc-modes` buttons) shows one map at a time; `<GameMap key={mode}>` remounts on switch (resets zoom/pan) while base state is lifted to the page (`basesByMode`) so each mode keeps its own layout. The 256×256 map grid is rotated 45° inside a `<g transform="rotate(45, 128, 128)">` to display as a diamond. The map lives in a **square `.sc-mapframe` container with `overflow:hidden`** (NOT a diamond clip-path anymore): at min zoom (1×) the whole diamond is inscribed with dark corner triangles; zooming in grows the diamond until it fills the box. Building images (City Hall, Armories, Player Base) are rendered **outside** the rotation group at pre-computed SVG root coordinates (`toSvg()` helper) so they appear upright; grid footprint tints remain inside the rotation group. **Interaction** uses unified Pointer Events with `touch-action:none`: drag empty area to pan, drag a base to move it (snaps to valid tiles), tap a base to select; two-finger pinch and mouse wheel zoom around the anchor point (wheel is a native `passive:false` listener); floating `.sc-zoomctl` +/−/reset buttons. Latest zoom/pan/bases are mirrored into `stateRef` (updated in an effect, not during render) for the native/pointer handlers. **Multiple player bases**: added from the right-hand `RosterPanel` (`+ Add Base` → `findFreeSpot`), auto-named "Player N", assigned to one of 8 color groups (1 red / 2 blue / 3 green / 4 yellow / 5 orange / 6 purple / 7 cyan / 8 pink via `GROUPS`; `.sc-swatches` is a 4-col grid so the 8 swatches wrap). Each roster row supports inline rename, group reassignment (color swatches), and delete. **Multi-select + tandem move**: selection is `selectedByMode[mode]` (a `string[]` of base ids, per mode, not persisted). Each roster row and each group header has a checkbox (`Check` component sets `indeterminate` via ref); the group checkbox selects/deselects all its members. Markdown bodies are still fully supported (all the pre-CMS guides are raw Markdown, and `parseGuideBody` falls through to Markdown for anything that isn't a blocks envelope) — the block editor has no table block, so for a guide with tables click **"Switch to Markdown"** in the body box *before* pasting. Tables (`remark-gfm`), and the `[!TIP]`/`[!NOTE]`/`[!WARNING]`/`[!IMPORTANT]`/`[!F2P]` callouts handled by `processCallouts`, both render. Frontmatter `title`/`author`/`pubDate` are shown in the page hero, so don't repeat an `# H1` or a "Published on:" line in the body — several older guides do and print their headers twice.

**Guides belong to a game (2026-10-16).** `guides.game` (`'dcdl'` default | `'godforge'` | `'invokers'` | `'voidhunters'`, check constraint `guides_game_check`) picks the section: `src/lib/guide-games.ts` (`GUIDE_GAMES`, `guidePath`) is the one list, the editor has a Game picker, the review queue shows where a draft will publish, and `getGuidesFull/getGuidesList/getGuide(…, game)` default to `'dcdl'` so every DCDL page is unchanged and another game's guide 404s at a DCDL URL. Godforge, Invokers and Void Hunters guides list on each game's hub (`/games/godforge`, `/games/invokers/guides`, `/games/void-hunters/guides`) and render at `<base>/[id]` (`/games/godforge/guides` itself 308s to the hub); those three games share `src/qgg/components/WorldGuidePage.tsx` (`WorldGuideArticle`, `WorldGuideCards`, and `WorldGameNews` for the hub's latest patch notes + codes). **Patch notes and codes are per game too:** `patch_notes.game` and `game_info.game` use the same ids (`game_info` is one row per game, id = position in `GUIDE_GAMES`), `getPatchNotes(game)` / `getGameInfo(game)` default to DCDL. Rendering is shared: `src/dcdl/lib/guide-render.ts` (body → HTML + TOC) and `src/dcdl/components/guide/GuideBody.tsx` (summary box, article, TOC); each game's page supplies its own hero. A new game needs a `GUIDE_GAMES` entry, the constraint widened, a `[id]` page and its sitemap lines. **Drafts** are `status='pending'` rows: hidden publicly (RLS + filter), marked "DRAFT · not public" in `/admin/content`, previewable in Studio → Review Queue ("Read draft"), and an admin save keeps them pending until approved there.

**Guides-500 — FIXED 2026-10-01 (confirmed in production: unknown slug → 404).** Every guide URL not prerendered at build time used to return **500** in production, so a guide added via the CMS editor stayed invisible until the next deploy. Root cause: `guide-blocks.ts` imported `isomorphic-dompurify` at module scope, which pulls in jsdom → html-encoding-sniffer (CommonJS) → `@exodus/bytes` (ESM-only), throwing `ERR_REQUIRE_ESM` when the serverless function loaded it. `sanitizeInline()` now uses **rehype-parse + rehype-sanitize** (parse5, no jsdom) with a closed allowlist schema (`INLINE_SCHEMA`, where `className` lists its allowed values), so the same code runs in the browser editor, on save, and at render. `isomorphic-dompurify` has been removed. **Do NOT bring jsdom back into anything the guide page imports.** A local `next start` never reproduced this bug, so verify on a deployed URL: an unknown slug should 404 and a guide created after the deploy should 200.

Separately, a build-ordering fact that remains true regardless: `generateStaticParams()` reads the `guides` table at **build** time, so a row must exist and be `status='approved'` *before* the deploy runs to be baked in as a static page.
